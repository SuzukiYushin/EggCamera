# エラーが起き得る箇所の一覧と注入テスト

長期運用テスト中、以下のカタログから**低確率（サイクルの8%）で順番に1つ**をわざと起こします。
さらに注入時は低確率で **2つ同時:15% / 3つ同時:7% / 4つ同時:3%** の多重注入を行います
（ローテーション位置はリロードを跨いで保存されるので、全項目が順番に網羅されます）。

## エラーカタログ

| # | ID | 箇所・場合 | 注入方法 | 期待される挙動 |
|---|----|-----------|---------|--------------|
| 1 | `session-create` | セッション作成 `POST /api/sessions` | fetchフックで 500 を返す | お詫びオーバーレイ → 10秒後自動リロード → トップ |
| 2 | `capture-502` | 撮影API（Mac到達不能相当）`POST /:id/capture` | fetchフックで 502 を返す | オーバーレイ → リロード |
| 3 | `capture-server` | 撮影トリガー（サーバ内部）| サーバの chaos API で mac-unreachable を発生 | オーバーレイ → リロード |
| 4 | `frames-api` | フレーム一覧取得 `GET /api/frames` | fetchフックでネットワークエラー | **オーバーレイは出ない**。同梱フレームA/B/Cにフォールバックして続行 |
| 5 | `settings-api` | クロップ設定取得 `GET /api/settings` | fetchフックでネットワークエラー | **オーバーレイは出ない**。デフォルト設定で続行 |
| 6 | `composite-upload` | 合成画像アップロード `POST /:id/composite` | fetchフックで 500 を返す | オーバーレイ → リロード |
| 7 | `r2-server` | R2アップロード（サーバ内部） | サーバの chaos API で失敗させる | session.status=error → オーバーレイ → リロード |
| 8 | `qr-server` | QRコード生成（サーバ内部） | サーバの chaos API で失敗させる | 同上 |
| 9 | `session-poll` | アップロード完了ポーリング `GET /api/sessions/:id` | fetchフックで25回連続ネットワークエラー | ポーリング上限（20回）→ オーバーレイ → リロード |
| 10 | `js-error` | フロントのJS実行時エラー | MAINワールドで例外を投げる | window.onerror 捕捉 → オーバーレイ → リロード |

### カタログ外（自動でカバーされるもの）

- **画像読み込み失敗**（写真プレビュー/フレーム画像）: `loadImage` の reject → unhandledrejection → オーバーレイ（#10と同経路）
- **アップロード全体のタイムアウト**: 90秒で完了しない場合もオーバーレイへ

## 各エラー時に監視する項目

| 監視対象 | 方法 | アラート条件 |
|---------|------|------------|
| **サーバ金額（R2コスト）** | fetchフックで実際に外へ出たリクエスト数を1サイクルごとにカウント | composite >4回 / capture >8回 / session作成 >5回 で「リトライストーム検知」（コスト警告） |
| **Mac miniのフリーズ** | 30秒ごとに `/api/admin/disk` を5秒タイムアウト付きでヘルスチェック | 応答なしで「サーバ無応答」カウント。サーバログ `data/logs/` でメモリ/プロセス異常も確認 |
| **ブラウザのフリーズ** | 700ms間隔のtickの実測間隔を計測 | 4秒以上止まったら「イベントループ停滞」カウント |
| **エラーUIの正しさ** | `[data-section="error-overlay"]` の出現を監視 | 注入したのに出ない／注入してないのに出る／30秒経ってもリロードされない → 「想定外」カウント |

## 結果の見方（ポップアップ）

- **注入** = わざと起こしたエラー数
- **オーバーレイ** = お詫び画面が表示された回数
- **想定外** = 期待と違う挙動（フォールバックすべき箇所でオーバーレイ、注入なしでオーバーレイ=実バグ、など）
- **コスト警告 / サーバ無応答 / 停滞検知** = 上の監視のアラート数

**「想定外」「コスト警告」「サーバ無応答」「停滞検知」が0のまま回り続けるのが合格条件です。**
